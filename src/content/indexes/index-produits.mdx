Les produits utilisent des variantes de B+arbres, avec des formats et localisateurs différents. Le vocabulaire du manuel doit être ramené au chemin d’accès réel.

| Produit et organisation | Feuille principale | Localisateur secondaire |
| --- | --- | --- |
| MySQL InnoDB avec PK | Ligne de la table, ordonnée par PK | Valeur de PK |
| SQL Server sur heap | Pages de tas séparées | RID physique |
| SQL Server clustered | Ligne dans la feuille clustered | Clé clustered |
| Oracle heap | Tas séparé | ROWID |
| Oracle IOT | Ligne dans l’organisation indexée par PK | ROWID logique fondé sur PK |

InnoDB choisit une clé clustered même sans PK explicite, selon ses règles de clé unique admissible puis d’identifiant interne. SQL Server permet de choisir explicitement un autre index clustered que la PK. Oracle peut réutiliser un index admissible pour une contrainte : « une PK crée toujours un nouvel index » est trop absolu.

### Oracle, exercice guidé

```sql
CREATE TABLE team (
  team_key VARCHAR2(3) PRIMARY KEY,
  team_name VARCHAR2(50),
  country_key VARCHAR2(3)
) ORGANIZATION INDEX;

SELECT index_name, blevel, leaf_blocks, distinct_keys
FROM user_indexes
WHERE table_name = 'TEAM';
```

La hauteur en niveaux vaut BLEVEL+1. BLEVEL=2 indique trois niveaux, et non deux. Le ROWID d’un heap encode un emplacement, mais certaines opérations peuvent le modifier ; ce n’est pas un identifiant métier éternel. Une IOT utilise des localisateurs logiques et parfois une indication d’emplacement pour éviter une descente supplémentaire.

L’index Oracle `REVERSE` inverse des octets de clés et peut réduire un point de contention sur insertions monotones ; il détruit l’ordre naturel des plages. Il ne faut pas le confondre avec indexer la chaîne renversée pour chercher un suffixe.

Les statistiques USER_TABLES et USER_INDEXES décrivent le moteur Oracle, jamais les résultats du moteur DuckDB de ce site. Les conseils chiffrés de remplissage p.68–72 restent des exemples : ils ne fixent pas une valeur universelle de page ou de fan-out.
