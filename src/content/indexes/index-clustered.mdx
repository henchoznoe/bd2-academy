Un index clustered, ou organisation plaçante dans le modèle du cours, range les lignes dans ses feuilles selon sa clé. Un index nonclustered stocke dans ses feuilles une clé et un localisateur vers les lignes conservées ailleurs. Un seul ordre physique principal peut organiser une table ; plusieurs index secondaires sont possibles.

### Dessin verbal de la page 99

À gauche, la racine et un niveau intermédiaire pointent directement vers les pages de données qui constituent les feuilles : organisation clustered de trois niveaux. À droite, les feuilles sont encore des pages d’index et leurs pointeurs partent vers des pages de données séparées : index nonclustered de deux niveaux d’index, suivi du lookup. Les deux possèdent un chaînage entre pages ; ce seul chaînage ne permet pas de les distinguer.

### Exemple de coût

Pour une organisation clustered de hauteur 3, trouver une ligne via la clé demande jusqu’à trois pages, feuille de donnée comprise. Pour un secondaire de hauteur 2 pointant directement vers une page de tas : jusqu’à deux pages d’index puis une page de donnée. Ces totaux deviennent des lectures **logiques** si les pages sont déjà en cache.

Si le localisateur secondaire est une clé primaire plutôt qu’une adresse physique, le lookup peut imposer une nouvelle descente dans l’index principal. Une requête couverte n’en a pas besoin.

Pour une plage de 10 000 lignes, des données regroupées peuvent tenir dans quelques centaines de pages successives. Des références dispersées peuvent causer beaucoup de lectures aléatoires. Le coût dépend des pages distinctes et du cache, pas seulement du nombre de lignes.

Ne pas assimiler clé primaire et clustered sans préciser le moteur. Ne pas non plus conclure qu’un index est creux parce que son niveau interne n’énumère pas toutes les clés : regarder les feuilles et les lignes réellement référencées.
